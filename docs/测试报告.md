### 星级评分（51 项）

理论下界 `par`（`minPulsesToClear`，**照度场模型下**）：

| 关卡 | par | 三星线 | 二星线 |
|---|---|---|---|
| 教学：初鸣 | 2 | 3 | 4 |
| 初次回响 | 2 | 3 | 4 |
| 隔墙之声 | 2 | 3 | 4 |
| 回声走廊 | 3 | 4 | 6 |
| 共振核心 | 4 | 5 | 8 |

- ✅ **每关的理论下界都不超过朴素上界**（par 可达，5 关全部满足）
- ✅ 理论下界至少为 1；随机关卡的 par 始终落在 `[1, 节点数+1]` 内（最大 par=5）
- ✅ 阈值单调：三星线 ≤ 二星线；三星线**等于** `par + 1`（保留一次探路容错）
- ✅ 边界：达到三星线即三星、刚好超过降二星、达到二星线仍二星、超过降一星
- ✅ 星级随脉冲次数单调不增（0→40 逐点验证）
- ✅ `par ∈ {2,3,4,5}` 时"正好 par 次 / par+1 次都是三星、par+2 次掉二星"，即三星仍有代价
- ✅ 极小 `par ∈ {0,1,2}` 时三星阈值不为 0（不会退化成"白送三星"）
- ✅ **会话接线**：`LevelSession.parPulses` 与 `minPulsesToClear()` 结果逐关一致
- ✅ **朴素最优打法通关且拿到三星**（阈值放宽后容错足够）
- ✅ **回波模型正确性**：脚本先补一发波照亮出口再走过去，
  确保测的是"玩家真实能做的操作"而非开全图挂

> **阈值改过一轮**：`par`（严格）→ `par + 1`。
> 严格 `par` 下 `par = 2` 意味着"照到节点与出口后各只发一次波、且一次走对位置"，
> 真人首通几乎必然只有 1~2 星，评分从"没有区分度"的极端滑到了"拿不到"的另一个极端。
> 相关断言同步改为三连验证（`= par` / `= par+1` 均三星，`= par+2` 降二星）。

> **`par` 随模型走**：切换声波模型（`bfs ↔ field`）会改变实际感知半径，
> 从而改变"最少几次脉冲能覆盖全部节点"，`par` 与星级阈值必须同步。
> `bfs` 下 `par = 2/2/2/2/3`；`field` 下 `par = 2/2/2/3/4`（后两关各多一次，
> 因为出口与节点之间的距离超过了照度场的有效半径，无法被同一次脉冲顺带覆盖）。
> 这正是 `minPulsesToClear()` 接收整个 `SonarConfig` 而非单个 `maxRange` 的原因——
> 评分与玩法必须共用同一套传播规则，否则会悄悄错位。

## 三之零点五、重绘后的两处回退修正（墙可见度 / 声波强度）

「去 AI 味」时把画布也一并"收敛"了，**收敛过头**，产生两个真实缺陷。
这两项都是**功能性**问题（影响玩家能否读懂画面），不是审美偏好，因此回退。

### 缺陷 A：墙与地面明度差不足，分不清能不能走

| | 重绘时（错误） | 修正后 |
|---|---|---|
| `wallFill` | `#14181c` | `#080a0c`（近黑） |
| `floorFill` | `#242a30` | `#2b323a`（中灰） |
| 明度差 | 极小，墙"陷进"地面 | 一眼可辨 |

另外给墙加了**斜纹质感**（`tile >= 9` 时绘制），和地面的方格细网格在**纹理维度**上区分；
墙描边透明度 `.42 → .6`，并加 `0.35` 下限兜底，
保证记忆层淡下去之后墙的轮廓不会一起消失（否则忘了墙在哪就会撞上去）。

### 缺陷 B：声波强度被压低到几乎看不见

重绘把声波各层的 `globalAlpha` 与 `pulseCore` 一起压暗，导致脉冲几乎不可见——
而声波是玩家获取空间的**唯一手段**，属于可用性，不属于"界面装饰"。

| 图层 | 重绘时（错误） | 修正后 |
|---|---|---|
| 主波前 | `alpha 0.7` / 线宽 `2` | `alpha 1.0` / 线宽 `2.5` |
| 拖尾 | `alpha 0.24` | `alpha 0.5` |
| 发射闪光 | `alpha 0.75` | `alpha 0.9` |
| 雾带 | 纯白 `alpha 0.3`（叠成灰环） | **青色** `alpha 0.18`（读作"雾"） |
| `pulseCore` | `#a9e4ee` | `#c8f2fa` |
| 点亮闪烁 | `flash * 0.85` | `flash` |

> **结论**：审美上的"克制"只适用于界面外壳；玩法反馈（声波 / 受击 / 通关）的
> 信息强度属于可用性，不能跟着一起压。这条已写入 README 与 MEMORY.md。

## 三之零点七、手柄适配验收（36 项通过 / 0 失败）

脚本：`.tmp/verifyGamepad.mjs`（1280×900 · headless Chrome · CDP 自动化）

### 怎么在没插手柄的机器上测

**注入假手柄，但覆盖的是浏览器 API 本身**，不是游戏内部的开关：

```js
Object.defineProperty(navigator, 'getGamepads', { value: () => [window.__pad] });
```

`GamepadController` 每帧读的就是 `navigator.getGamepads()`，所以走的是与真机
**完全相同**的代码路径（快照读取 → 边沿检测 → 折算 GameAction → 优先级链）。
这是这套验收唯一诚实的做法：逻辑接线可回归，手感不可。

按键通过改写 `window.__pad.buttons[i]` 的 `pressed` / `value` 触发；
点击时长取 **90ms**——明显长于一帧（~17ms，保证被 `poll()` 采样到），
又明显短于移动节流 150ms（否则一次按键会走两格）。

### 修复记录（本轮发现的真实缺陷）

1. **`#editor-grid-wrap` 缺失**：编辑器网格容器写了 `class` 却漏了 `id`，
   导致 `EditorScreen` 构造函数抛错、整站白屏（首页 DOM 已渲染但 JS 中断）。
   已补上 `id`，并新增一个脚本性的 **ID 一致性检查**：扫描 `src/**/*.ts` 中所有
   `requireEl()` / `getElementById()` 的字面量 ID，与 `index.html` 逐个比对。
2. **分享码校验和过弱**：初版校验和只覆盖 `RLE~宽~高`，标题段被改不会报错。
   已把 `编码标题` 也纳入校验和计算。
3. **测试脚本自身的按键时长错误**（非游戏缺陷，但会导致验收结论失真）：
   游戏支持"按住连续移动"，节流间隔 **150ms**；验收脚本原本按住 170ms，
   于是**一次按键走两格**，路径逐格错位并级联失败。实测阈值：

   | 按住时长 | 20 / 60 / 100 / 140 ms | 170 / 250 ms | 400 ms |
   |---|---|---|---|
   | 实际位移 | 1 格 | 2 格 | 3 格 |

   已把按住时长改为 **80ms**（明显小于 150ms 又大于一帧 ~17ms），
   并给走位加上"逐步核对 + 一次重试"，杜绝静默错位。

### 修复记录（陷阱机制引入时发现的真实缺陷）

5. **`minSpikeCostToClear` 的 0-1 BFS 双端队列前后指针混用**：
   初版用同一个 `head` 既做"已消费下标"又做"队首插入位置"，导致压到队首的
   0 权节点永远读不到。改为 `front` / `back` 两个独立指针，
   缓冲区以中点为起点（容量 `size*4+16`）——这是踩过两次坑之后才稳定的写法。
6. **`minSpikeCostToClear` 最后一段查了错误的距离场**：
   "最后一个节点 → 出口"误用了"出口视为墙"的距离场，出口永远是 `INF`，
   所有关卡都被误判成打不过去。改为准备两套场：`blockedFrom[]`（激活节点阶段）
   与 `openFrom[]`（最后一段），并把这段踩坑原因写进注释。
7. **「隔墙之声」原本放了一排躲不掉的尖刺**：3 颗尖刺落在只有一格宽的唯一通道上，
   分析器算出最少代价 3 = 生命上限 3，这一关实际**无法通关**（旧提示"可以绕远路避开"是错的）。
   已重做该段地形为两格宽走廊，尖刺堵在房间门口、可从上一行绕开，代价降为 0，
   提示文案同步更正。
8. **「共振核心」的尖刺必然落在必经之路上**：该迷宫最窄处只有一格宽，
   分析器算出最少代价 2。与其削减尖刺让最终关变得没有压力，不如显式把
   `maxHealth` 覆盖为 4（保留"必须硬吃两次"的压迫感，另留 2 点容错），
   并在关卡定义里写清这条取舍的理由。
9. **随机关卡会产出"理论上能过、实际像运气"的图**：
   分析器算的是**最优路线**代价，而人会走得不完美。实测存在
   `minSpikeCost=1` 但按直觉最短路径会连踩 3 次的随机图——正好是要避免的失败模式。
   已在 `buildRandomMap` 的自检里追加 `RANDOM_SAFETY_MARGIN = 2`，
   要求 `minSpikeCost <= maxHealth - 2`，不自洽就换派生种子。
10. **编辑器在"只有提醒、没有错误"时不给正面反馈**：
    尖刺带来的"最优路线仍需踩中 N 次尖刺"是警告而非错误，但旧逻辑只在
    "无错误且无警告"时才显示"校验通过"，于是这类地图只剩一条黄字提醒，
    看起来像不能玩。已改为只要无错误就明确给出"校验通过（有提醒），可以试玩 / 分享"。

### 测试脚本自身的两处坑（不影响游戏，但会让结论失真）

11. **地图 fixture 行宽不一致**：多处手工写的测试地图有一行多了一个字符
    （如 `#S^.^.*.E#` 是 10 宽，而边框是 9 宽），导致 `decodeShareCode` 抛异常，
    看起来像"分享码往返失败"，实际是 fixture 写错了。已引入一次性扫描
    （逐行比对同一数组内所有地图串的长度）把这类问题全部揪出来并修正。
12. **模拟通关时按数组顺序走访节点，而不是分析器给出的最优顺序**：
    随机迷宫经过编织，节点访问顺序会显著影响踩刺次数，
    按数组顺序走会多踩几次，看着像"分析器算错了"。已新增 `optimalVisitOrder()`
    导出最优顺序，并让校验脚本按它实走；同时把断言改为
    "分析器代价 >= 实走踩刺数"（偏保守即安全），而不是要求两者严格相等。

### 收尾复查时补发现的两处真实缺陷

13. **编辑器的「一键生成迷宫」调用了不做自检的生成函数**：
    `fillMaze()` 直接调 `generateMapRows()`，绕过了 `buildRandomMap()` 里的
    `RANDOM_SAFETY_MARGIN` 自检，因此大约每点几次就会产出一张
    最优代价 ≥ 生命上限的图——编辑器自己的 `refresh()` 立刻把它标成
    "无法通关"。玩家视角就是"点了生成，结果说这图不能玩"。
    已改用 `buildRandomMap()`（内部会换派生种子重试，极端情况退化为必定可玩的简单房间），
    并在调用处写清为什么不能用前者。
14. **编辑器保存后返回，列表不刷新（刚存的关卡"消失"）**：
    `LevelSelect.show()` 只在切页签时渲染列表，而"保存 → 试玩 → 通关 → 回到编辑器 →
    返回关卡中心"这条路径里 `show()` 不会被再次触发，于是列表停在保存前的快照上。
    数据其实已经写进 `localStorage`（`resonance-field:custom:v1` 里确实有记录），
    只是 DOM 没重画——玩家会以为保存没生效，甚至重复保存。
    已新增 `LevelSelect.refreshCustom()` 并在 `saveCustom()` 里调用。

### 修复记录（星级评分引入时发现的真实缺陷与建模错误）

15. **星级阈值在"没有区分度"与"拿不到"之间来回摆过两次**：
    第一次把三星线设成 `par + 1`，但当时 `par` 口径偏松，主线五关的 `par`
    恰好等于"走到每个节点各发一次"的朴素打法（L1~L4 = 2 次、L5 = 3 次），
    于是**任何正常通关都直接三星**，评分等于没做；
    收紧成严格 `par` 之后又走到另一个极端——`par = 2` 意味着
    "照到节点与出口后各只发一次波，并且一次走对位置"，
    而真人不知道最优发射点在哪，首通几乎必然只有 1~2 星。
    **最终定在 `par + 1`**：保留"你得真的规划过"这条底线，同时给一次探路容错。
    断言也从"多打一发就掉二星"改为三连验证（`= par` / `= par+1` 均三星，`= par+2` 降二星）。
16. **`par` 里"+1"的来源一度被误判为多余**：
    校验脚本最初按完美寻路直接走进出口，实测脉冲数**低于** `par`，
    让"三星有真实代价"这条断言假性失败，看起来像分析器算错。
    查明真因在渲染层——**出口必须先被脉冲照亮才会画出来**
    （`CanvasRenderer.drawExit` 中 `alphaFor(exit) <= 0.001` 直接 return），
    玩家在照到出口前根本不知道它在哪，所以那一发是必需的。
    脚本已改为"出口未照亮就先补一发波再走过去"。
17. **校验脚本的 `settle()` 漏推进时间，导致 `emitPulse()` 静默失败**：
    `PulseSystem` 有 0.6s 冷却，脚本连续调用 `emitPulse()` 却不推进帧，
    只有第一发成功，实测脉冲数远小于预期，整段断言失去意义。
    已在每次发射之间推进 3 秒（90 × 1/30s）跨过冷却。
18. **`ProgressData` 新增字段的默认值被复用同一对象**：
    改为 `emptyProgress()` 每次返回全新容器，
    避免默认对象被调用方改写后污染后续所有存档读取。

### 修复记录（照度场模型引入时发现的真实缺陷）

22. **45° 射线从两堵墙的夹角穿过去**（本轮最严重的一个缺陷，属算法错误）：
    照度场最初按"沿方向每次前进半格、再取 `floor` 得到所在格"实现。
    起点取格心偏移 `(x+0.5, y+0.5)` 后，对角方向的采样位置序列是
    `(x±0.5, y±0.5) → (x+1, y+1) → …` —— 每两步精确落在**整数格点**上。
    `Math.floor(2.0)` 只会判给 `(2,2)`，于是 `(2,1)` 与 `(1,2)` 两格**从未被采样**，
    声波从两堵墙的夹角里穿了过去（诊断中 `(2,2)` 照度读到 1.0，而它本应完全不可见）。
    改为 **DDA / Amanatides–Woo 逐格步进**：用"到下一格线的参数化距离"推进，
    每步必进一格且落在格内；同时在对角同时跨两条格线时，把相邻两格都做一次墙判定。
    校验脚本新增一个夹角形状的回归用例长期守住这一点。
23. **对角方向每格衰减了两倍**：早期实现里给对角乘 `falloff²`（理由是"对角位移是 √2 倍"），
    但那是把"射线能量随欧氏距离衰减"和"DDA 每轮前进一格"混为一谈。
    DDA 每轮恰好跨一格，8 个方向应共用同一系数；否则同一圈上的正交格亮、对角格暗，
    画面是八角星而不是等能圆。改为统一 `falloff` 后，
    "正交与对角在 1 格 / 2 格距离上照度一致"两条断言同时成立。
24. **相邻格照度为 1.0 而不是 `falloff`**：原来先落账再衰减，
    导致起点与相邻格同为满照度，画面上出现"最内圈一圈一样亮"的断层。
    改为**先衰减再落账**，相邻格 = 0.86。
25. **评分与玩法模型不一致的风险（预防性修复）**：
    `mapAnalysis.pulseCoverage()` 原本直接调 `propagate()`，切到照度场后若不改，
    会出现"评分按 BFS 算 par、游戏按照度场跑"的静默错位——
    玩家按最优解打完却拿不到三星。改为按 `SonarConfig.model` 分派，
    并让 `minPulsesToClear()` 接收整个 `SonarConfig`（而非单个 `maxRange`）。

### 修复记录（自定义关卡分享码空白）

26. **「我的关卡 → 分享码」生成空白**（用户反馈：「自定义关卡的分享码有bug，会生成空白」）。
    编解码算法本身没有问题，是 `GameApp.levelFromRecord()` 里把分享码写死了：

    ```ts
    code: undefined,   // ← 根因
    ```

    这个 `LevelDefinition` 同时服务两件事：①「试玩」时喂给关卡系统；
    ②「分享码」弹窗取 `code`。而两个消费方都写的是 `level.code ?? ''`：

    | 调用方 | 触发时机 | 结果 |
    |---|---|---|
    | `shareCustom(id)` | 「我的关卡」列表的「分享码」按钮 | **空白** |
    | `saveCustom(...)` | 编辑器保存后自动弹出的弹窗 | **空白** |
    | `EditorScreen.buildLevel()` | 编辑器内部的「分享」按钮 | 正常（另一条路，`code` 有真值） |

    **为什么长期没被发现**：编辑器自己那条路是好的，验收脚本也只测了那一条。
    已改为 `code: this.shareCodeOf(record)`（现算 `encodeMapCode`），
    并给 `shareCodeOf()` 加 try/catch —— `encodeMapCode` 对空地图会抛错，
    而 localStorage 里的记录理论上可能被外部改坏；拿不到码就返回空串，
    由 `shareCustom()` 明确提示「《xx》内容为空，无法生成分享码。」，
    而不是让异常冒到主循环把整局游戏打断。

    **同时暴露的测试方法问题**（比缺陷本身更值得记）：原脚本这一步只断言了弹窗标题——

    ```js
    check('保存到我的关卡后给出分享码', savedTitle.includes('已保存'), savedTitle);
    ```

    「标题含『已保存』」就放行，**textarea 是空的也照样 PASS**。
    已补 6 项断言（`verifyFeatures.mjs` 65 → **71 项**）：保存后弹出的码**非空**、
    与编辑器导出**字节级相等**，以及**此前零覆盖**的列表路径
    （`#custom-list .custom-item:first-child .custom-actions .mini-btn:nth-child(3)`）
    单独走一遍「弹窗打开 / 码非空 / 格式可解析 / 与编辑器导出一致」。

    > **泛化原则**：断言「弹窗打开了」「标题对了」是**弱断言**。
    > 只要被展示的数据是动态生成的，就必须**去读那个数据本身**
    > （textarea 的 `value`、列表条数、画布像素），否则「空数据 + 正常外壳」
    > 这类缺陷会 100% 溜过验收。
    > 同类前科：缺陷 14「保存后列表不刷新」也是数据在 `localStorage` 里、
    > DOM 是空的 —— 靠改读 DOM 数量才抓到。

### 修复记录（分享码可读化外形）

27. **"把分享码加密一下、看起来更美观"**。这里**没有加密，只做了可读化外形**，
    理由写进了 README「关于『加密』」小节：纯前端 + 全开源的约束下，
    密钥必然随码发出，加密换不到任何机密性，却要付出"码变长 / 出错难查 /
    破坏纯文本可粘贴"的代价，还会给人虚假的安全感。
    实际改动是**外形**：`RFM1~…` → `RESO·…`，`RFR1~…` → `RESE·…`（全角中点分隔），
    并在分享弹窗加**字符计数**（长码 180~500 字符，3 行窗口看不全，"有多长"本身是有效信息）。

    改动落在三处，**且必须三处同时改**——
    编辑器导出、随机种子码复制、两个分享弹窗（保存后 / 列表 / 通关面板）：
    统一走 `toFriendlyCode()`；解码侧在 `normalizeShareText()` 一处收口，
    所以校验和、尺寸检查、RLE 校验这些真正重要的逻辑**一行未动**。

    **本轮踩到并修掉的三个真实缺陷**（都是"换外形"引入的，且都会静默错）：

    | # | 缺陷 | 症状 | 根因 |
    |---|---|---|---|
    | ① | 两种码统一成 `RESO·` | 随机码全被当成地图码解析，报"尺寸 20261012×10 超出范围" | 前缀是解码侧**唯一的类型判别依据**，统一就丢了类型信息 |
    | ② | 规范化时对整串 `toUpperCase()` | 原样复制的码报"分享码校验失败" | 标题段是 base64url（大小写是载荷）+ RLE 的 36 进制计数是**小写字母**，大写后 `rleDecode` 的 `[0-9a-z]` 扫描在字母处停下、整段错位 |
    | ③ | 顺手认"半角点"当分隔符 | 同样是"原样复制的码报校验失败" | `.` 正是地图字符（地面），全局替换把地图内容改坏了 |

    修法：① 保留两个不同前缀；② `normalizeShareText` **只规范前缀，其余字段原样保留**；
    ③ 撤回半角点容错 —— 分隔符容错到此为止，宁可让手打的码报格式错误，
    也不能冒改坏地图的风险。

    **顺带发现的一个已有问题**：验收脚本里那句
    `check('非法分享码…', ...)` 用的样例是 `'RFM1~9~9~1#~zz'`，
    改外形后它**依然"通过"**——因为它本来就是非法码，被拒绝是预期行为，
    所以格式变了也不会暴露。真正需要盯的是**合法码**的那几条断言。

### 修复记录（损坏记录产出"空白分享码"）

28. **用户反馈「分享码依旧未修复」**。排查后确认**这是另一个独立缺陷**，
    与缺陷 26（`levelFromRecord` 写死 `code: undefined`）不是同一回事：

    **触发条件**：localStorage 里的自定义记录被改坏成 `map: ['']`
    （一行空字符串）。这不是理论情况——`CustomLevelStore.load()` 只校验
    "是字符串数组"，**不做任何地图合法性检查**，所以被外部工具改过的存档、
    或早期版本写入的空行，都能直接进入列表。

    **症状**：点「分享码」**弹出的是一个几乎空白的弹窗** ——
    textarea 里是 `RESO·0·1··si·5Z2P6K6w5b2V`，尺寸段是 `0`、游程段是空，
    有效可见内容只有开头那一小截。用户看到的就是"分享码又没生成出来"。

    **根因**：`encodeMapCode()` 只检查了 `rows.length === 0`，
    **没检查行宽**。首行是空串时 `width = 0`，于是它一路编码成功，
    产出宽度 0 的码。而这条码**连自己的解码器都不接受**
    （"分享码尺寸 0×1 超出允许范围（5~61 × 5~41）"）——
    等于生成了一条谁也导入不了、还长得像"空白"的死码，比直接报错更糟。

    更值得记的一点：`shareTextOf()` 的 `try/catch` **拦不住它**，
    因为它在编码侧完全"合法"、根本不抛错。**只知道用异常做防御是不够的**。

    **修法（三层，从源头到界面）**：
    - **源头**：`encodeMapCode()` 补上 `width === 0` 与"行宽不一致"的校验，
      判据与 `analyzeRows()` 对齐（它同样以"首行长度为 0"为硬错误），
      这样"能不能编码"和"能不能游玩"不会变成两套标准；
    - **防线**：`shareTextOf()` 在编码之后再**自解一遍**，解不开就当作没有码。
      这一层是防御性的 —— 它保证"弹窗里出现的码，一定能被别人导入"，
      无论将来上游又漏了哪种非法输入（比逐个枚举非法输入的断言更耐久）；
    - **界面**：`shareCustom()` 与 `saveCustom()` 在码为空时给出明确提示
      「内容为空或已损坏，无法生成分享码。请打开编辑器确认地图至少有一行内容」，
      **不打开弹窗**。注意 `saveCustom()` 原先**根本没有**空码检查
      （只有 `shareCustom()` 有），这次一并补上。

    **验收断言方式**：注入坏记录后点「分享码」，断言**弹窗不可见** +
    提示文案含"无法生成分享码"。仍然读"数据本身"（弹窗可见性 / 提示文案），
    不是"按钮点到了"——这是本项目从缺陷 26 起就定下的规矩。

    **这段用例故意放在脚本最后**：它需要 `Page.reload` 才能让
    `CustomLevelStore` 重读 localStorage，而 reload 会把整页状态清零。
    第一版把它插在第 6 段中间，reload 直接打断了前面建立的
    "编辑器 / 列表 / 计数"上下文，**导致一批无关断言级联失败**
    （通关面板、导入计数、甚至更早的段落全红）——症状看起来像"功能坏了"，
    其实是**用例摆放位置**的问题。

    **一个被断言抓出来的、但属于"用例自身"的错误**：
    泛化断言「凡能生成的码都能被自己的解码器接受」第一版放了张
    11×1 的"单行地图"，被拒绝了 —— 但那是**解码器的尺寸校验在正常工作**，
    不是缺陷。换成真正合法（尺寸落在 `MAP_LIMITS` 内）的地图后通过。
    记这一笔是因为它说明：断言失败时**先确认用例本身合不合法**，
    再下"功能有 bug"的结论。

   也不做内容审核；导入他人分享码等价于加载他人编写的数据（目前只有地图，无脚本）。
7. 随机迷宫的"好玩程度"未做主观质量评估：只保证**结构合法且一定可通关**，
   不保证每张图的探索节奏都理想；陷阱机制上线后额外保证
   "最优路线代价还留 2 点容错"，但仍不能保证每张图的陷阱都布置得有意义
   （可能出现尖刺全部散在死胡同里、永远踩不到的情况）。
8. **陷阱的"感知"依赖玩家主动发脉冲**：如果玩家一路不发声波闷头走，
   陷阱就退化成纯运气。这是刻意的设计（惩罚不使用核心机制的行为），
   但教学关之外没有强制引导；实际手感需要通过真人试玩评估，本轮未做。
9. **生命值只有整数档、没有回复手段**：容错完全依赖关卡设计的余量。
   若后续要加"回复"，建议做成关卡级 `hazard.healOnResonator`（已预留该字段）而非全局开关。
10. **星级只看脉冲次数、不看用时**：这是有意的（脉冲才对应"有没有在动脑"），
    但副作用是"慢慢走、少发波"和"快速走、少发波"拿同样的星。
    使用时长仍单独记录（`bestTimes`），只是不参与评级。
11. **`par` 是理论下界，需要一次探路容错**：对 L1~L3 而言 `par=2`（照度场模型），
    要求玩家在照到节点与出口后各只发一次波、且一次走对位置。
    真人不知道最优发射点在哪，所以三星线放宽到 `par + 1`——多一次试错仍可三星。
    这条路仍要求"规划过"，只是不再要求"零浪费"。
12. **星级阈值未做真人难度校准**：三星线由 `par + 1` 机械推导，
    只经过自动校验（`par` / `par+1` 均三星、`par+2` 降档），未做真人试玩手感评估。
    它在"没有区分度"和"拿不到"之间已经摆过两次，当前值是设计判断而非实测结论。
    照度场模型上线后 `par` 又整体上移（`2/2/2/3/4`），这一项的紧迫性更高了。
13. **前端重绘只做了视觉层，未做无障碍审计**：对比度、焦点可见性、
    屏幕阅读器语义（尤其是画布内容）都未系统检查。
    现有 `aria-label` 只覆盖了星级与部分控件。
14. **照度场是"8 条射线采样"，不是真正的波动方程**：它给出距离衰减与遮挡，
    但没有衍射、反射、干涉；射线只有 8 个方向，斜向的最小角分辨率是 45°。
    如果后续要做"声波绕角"这类效果，需要把射线采样换成波前传播（或至少增加方向数）。
15. **照度场有效感知半径（约 5 格）短于 BFS（8 格）**，直接后果是
    出口与节点之间的距离普遍超过一次脉冲的覆盖范围，`par` 因此上升。
    这两个值由 `fieldFalloff` / `fieldThreshold` 决定，目前是设计取值，
    没有做"玩家在 5 格视野下是否会频繁迷路"的真人体验评估。
16. **两种模型只做了数值 A/B 对比，未做手感 A/B**：
    校验脚本确认了 `par` 与覆盖格数的差异，但"哪种更爽"没有真人对照实验。
    `model` 保留为开关正是为了方便日后切换后再评。
